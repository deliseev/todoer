# Разработка

Технический справочник по `todoer`: команды, API, устройство слоёв, соглашения об ошибках и тестах. О самом проекте и его правилах — [README.md](README.md), порядок работ и что уже закрыто — [PLAN.md](PLAN.md); `CLAUDE.md` — тот же текст по-английски для агента, его надо править вместе с этим файлом.

## Команды

Разработка идёт на хосте, в докере живёт только база. Поэтому начинается всё с неё:

```bash
docker compose up -d --wait db                   # Postgres на localhost:5432
export TODOER_DATABASE_URL='postgres://todoer:todoer@localhost:5432/todoer?sslmode=disable'
export TODOER_TEST_DATABASE_URL="$TODOER_DATABASE_URL"
go run ./cmd/todoer-migrate up                   # накатить схему
```

Порт переопределяется переменной `TODOER_DB_PORT`, если 5432 на машине уже занят.

```bash
go test ./...                                    # весь набор
go test ./... -race -count=1                     # обязательно перед сдачей работы
go test ./internal/domain/todo/ -run TestNewTitle -v   # один тест
go test ./... -run 'TestTaskMutations' -v        # группа по регулярке
go vet ./...
gofmt -s -l .                                    # должен молчать; -s ловит несокращённые литералы
```

Запуск сервера:

```bash
go run ./cmd/todoer                              # слушает :8080
TODOER_ADDR=127.0.0.1:9000 go run ./cmd/todoer   # другой адрес
```

Схема:

```bash
go run ./cmd/todoer-migrate up                   # накатить недостающие
go run ./cmd/todoer-migrate status               # что накатано
go run ./cmd/todoer-migrate down                 # откатить последнюю
```

`gofmt -s -l .` и `go test -race` — не формальность: оба ловили реальные дефекты в этом коде. Прогонять оба перед тем, как объявить работу законченной.

Ровно эти проверки крутит CI (`.github/workflows/ci.yml`) на пуш в `main` и на пул-реквесты в него: `gofmt -s`, `go vet`, поднятие базы через `docker compose up -d --wait db`, `go run ./cmd/todoer-migrate up`, `go test ./... -race -count=1`. Список в рабочем процессе и список здесь обязаны совпадать — разойдясь, зелёная сборка перестаёт что-либо значить.

**Без базы интеграционные тесты пропускаются, но не в CI.** Нет `TODOER_TEST_DATABASE_URL` — тест пропускается: на машине разработчика, у которого не поднят контейнер, это нормально. Нет переменной, но выставлена `CI` — тест падает: зелёная сборка, ничего не проверившая, хуже красной.

Быстрая сводка по красноте/зелени:

```bash
go test ./... -count=1 -v 2>&1 | grep -cE '^\s*--- PASS'
go test ./... -count=1 -v 2>&1 | grep -cE '^\s*--- FAIL'
```

## API

Аутентификации нет: клиент называет себя заголовком `X-Owner-ID`, и без него любой запрос — 400. У `POST /tasks` есть необязательный заголовок `Idempotency-Key`: с ним повтор возвращает ту же задачу тем же 201 и тем же `Location`, а тот же ключ с другим телом — 409. Тела запросов и ответов — JSON, времена — RFC 3339, необязательные поля в ответе уезжают как `null`, а не пропадают. Разбор строгий: неизвестное поле, второй документ в теле и тело больше 64 КиБ — отказ.

| метод | путь | ответ |
|---|---|---|
| `POST` | `/tasks` | 201, `Location` и `{"id":"…"}`; `Idempotency-Key` необязателен |
| `GET` | `/tasks/{id}` | 200, задача целиком |
| `PATCH` | `/tasks/{id}` | 200, обновлённая задача |
| `POST` | `/tasks/{id}/start` | 200, обновлённая задача |
| `POST` | `/tasks/{id}/complete` | 200, обновлённая задача |
| `POST` | `/tasks/{id}/cancel` | 200, обновлённая задача |

Подёргать поднятый сервер (команды рабочие, прогонялись целиком):

```bash
ADDR=localhost:8080
OWNER='X-Owner-ID: user-42'
JSON='Content-Type: application/json'

# создать; в ответ приезжают Location и идентификатор
ID=$(curl -s -X POST $ADDR/tasks -H "$OWNER" -H "$JSON" \
  -d '{"title":"Купить молоко","description":"Два литра","priority":"high","due_date":"2027-01-01T12:00:00Z"}' \
  | sed 's/.*"id":"\([^"]*\)".*/\1/')

curl -s $ADDR/tasks/$ID -H "$OWNER"                                            # прочитать

# сменить заголовок, не трогая остальных полей: чего нет в теле, того не касаются
curl -s -X PATCH $ADDR/tasks/$ID -H "$OWNER" -H "$JSON" -d '{"title":"Купить кефир"}'

# три состояния срока: null — снять, строка — назначить, поля нет — не трогать
curl -s -X PATCH $ADDR/tasks/$ID -H "$OWNER" -H "$JSON" -d '{"due_date":null}'
curl -s -X PATCH $ADDR/tasks/$ID -H "$OWNER" -H "$JSON" -d '{"due_date":"2027-02-01T09:00:00Z"}'

# переходы статуса — действия, а не поле
curl -s -X POST $ADDR/tasks/$ID/start -H "$OWNER"       # status: in_progress
curl -s -X POST $ADDR/tasks/$ID/complete -H "$OWNER"    # status: completed
```

Отказы, которые стоит попробовать там же (`-o /dev/null -w '%{http_code}\n'` покажет только код):

```bash
curl -si -X POST  $ADDR/tasks         -H "$JSON" -d '{"title":"x"}'              # 400: нет X-Owner-ID
curl -si -X POST  $ADDR/tasks         -H "$OWNER" -H "$JSON" -d '{"title":""}'   # 400: пустой заголовок
curl -si -X PATCH $ADDR/tasks/$ID     -H "$OWNER" -H "$JSON" -d '{"titl":"x"}'   # 400: неизвестное поле
curl -si          $ADDR/tasks/xyz     -H "$OWNER"                                # 400: негодный идентификатор
curl -si          $ADDR/tasks/$ID     -H 'X-Owner-ID: someone-else'              # 404: чужая задача
curl -si          $ADDR/tasks/00000000000000000000000000000000 -H "$OWNER"       # 404: задачи нет
curl -si -X POST  $ADDR/tasks/$ID/start  -H "$OWNER"                             # 409: выполненную не начать
curl -si -X POST  $ADDR/tasks/$ID/cancel -H "$OWNER"                             # 409: и не отменить
```

Идемпотентность создания — там же:

```bash
KEY="Idempotency-Key: $(uuidgen)"
curl -si -X POST $ADDR/tasks -H "$OWNER" -H "$JSON" -H "$KEY" -d '{"title":"Купить молоко"}'  # 201
curl -si -X POST $ADDR/tasks -H "$OWNER" -H "$JSON" -H "$KEY" -d '{"title":"Купить молоко"}'  # 201, тот же Location
curl -si -X POST $ADDR/tasks -H "$OWNER" -H "$JSON" -H "$KEY" -d '{"title":"Купить кефир"}'   # 409: ключ занят другим запросом
```

Заголовки в кавычках не случайно: `zsh`, в отличие от `bash`, не разбивает подстановку на слова, и `-H $OWNER` уехал бы одним аргументом — сервер ответил бы 400 на всё подряд.

## Архитектура

Четыре пакета и две команды: `internal/domain/todo` — чистое доменное ядро, оно не знает о хранилищах, транспорте и фреймворках и не должно узнать; `internal/app` — сценарии использования поверх него; `internal/infra` — реализации портов `app` (`SystemClock`), в подпакете `internal/infra/postgres` — хранилище со схемой и миграциями, в `internal/infra/outbox` — доставщик событий из исходящей очереди; `internal/transport/httpapi` — HTTP-адаптер; `cmd/todoer` — композиционный корень, `cmd/todoer-migrate` — команда миграций. Особняком стоят три обычных, а не `_test`, пакета: `internal/domain/todo/todotest` — доменные значения для тестов, `internal/app/apptest` — наборы тестов контракта для портов `app`, и `internal/infra/postgres/pgtest` — оснастка, поднимающая базы под тесты; в сборку приложения они не входят, но пакетами `_test` быть не могут, потому что их импортируют тесты разных пакетов. Зависимости направлены внутрь: `cmd` → {`transport`, `infra`} → `app` → `todo`, обратного знания нет ни на одном уровне.

**Внешние зависимости живут только в `internal/infra` и `cmd`.** Прежнее правило «только стандартная библиотека» отменено ради Postgres — драйвер `pgx` и мигратор `goose` написать самому нельзя, а научиться работать с базой так, как это делают в коммерческой разработке, — цель этого этапа. Заменившее его правило сохраняет то, ради чего вводилось прежнее: домен и сценарии по-прежнему обходятся стандартной библиотекой, и ни пул соединений, ни форматы проводного протокола, ни чужие представления времени внутрь не проникают.

**`infra` и `transport` стоят по разные стороны от `app`, и путать их нельзя:** `infra` — ведомая сторона, она реализует порты, которые объявляет `app`; `transport` — ведущая, он зовёт сценарии `app`. Поэтому HTTP и не живёт в `internal/infra`.

**Слои встречаются только в `cmd/todoer`.** Там и только там инфраструктура подставляется в порты сценариев, а транспорт получает собранный сервис. Подробности сборки — ниже, в разделе «Композиционный корень».

### Домен

**Агрегат — `Task`, и он один.** Транзакционная граница совпадает с одной задачей. Связи с другими агрегатами хранятся по идентичности (`OwnerID`), а не ссылкой на объект. `TaskList` появится позже отдельным агрегатом, хранящим имя и владельца, но не сами задачи. Это решение принято сознательно ради будущего шардирования и разнесения по сервисам — не переделывать его на «список как контейнер задач» без явной просьбы.

**Время в домен приходит параметром.** Каждый мутирующий метод принимает `now time.Time`. Агрегат никогда не спрашивает время сам и о часах не знает вовсе: порт `Clock` живёт у своего единственного потребителя — в `internal/app/ports.go`, реализация `SystemClock` — в `internal/infra`. Благодаря этому тесты домена работают с обычными константами и не нуждаются в моках.

**Значимые объекты валидны по построению.** `Title`, `Description`, `Priority`, `Status`, `DueDate`, `TaskID`, `OwnerID` — сравнимые структуры с приватными полями, создаются только через фабрики. Агрегат **не должен** перепроверять их содержимое или лезть в приватные поля: единственное, в чём он убеждается, — что вместо объекта не передали нулевое значение (`IsZero()`, `IsValid()`).

**У каждого правила ровно один носитель.** Имена статусов — `statusNames`, имена приоритетов — `priorityNames`, разрешённые переходы — `transitionMatrix`. И `String()`, и `Parse*()` читают одну и ту же таблицу. Добавление статуса или приоритета — правка одной таблицы, а не пяти `switch`.

**Мутаторы `Task` собраны из трёх приватных хелперов** (`task.go`):

- `ensureMutable()` — единственный guard, спрашивает `Status.IsTerminal()`, а не перечисляет статусы сам;
- `apply(now, event)` — обязательные три шага любой успешной мутации: `updatedAt`, `version++`, `append` события;
- `transitionTo(target, now, event)` — то же плюс сверка с `transitionMatrix`.

Новый мутатор писать по этому же образцу и обязательно заканчивать вызовом `apply`. Дублирование этих строк вручную уже приводило к четырём потерянным присваиваниям `updatedAt`.

**Повтор — не мутация.** Перед `apply` мутатор сверяет присланное значение с текущим и на совпадении возвращает `nil`, не трогая ни версию, ни события. Иначе клиент, присылающий форму целиком (а `UpdateTask` — именно такой сценарий), каждым сохранением рассылает «изменилось» по неизменившимся полям и двигает версию, отбирая оптимистичную блокировку у всех остальных: измеряли — PATCH со всеми полями, равными сохранённым, давал `version 1 → 5` и четыре события. Значимые объекты сравнимы, поэтому это `==`; для срока — `DueDate.Equal` (у `time.Time` `==` сличает не момент) и `sameDueDate` для необязательности, где `nil` значит «срока нет», а не «поле пропущено». Добавляя мутатор, добавить его и в `sameValueMutations()` в `task_test.go`.

**В `Reschedule` проверка повтора стоит раньше проверки срока, и порядок содержательный.** Перенос на уже стоящий момент — не перенос, требовать от него будущего не за что; задача с просроченным сроком законно живёт в хранилище, и вернуть ей её же срок — не то же самое, что назначить просроченный. Без этого круг `GetTask` → `UpdateTask` разрывался бы: `TaskView` отдаёт срок наружу, клиент возвращает форму целиком, и у просроченной задачи нельзя было бы изменить даже заголовок. Послабление касается ровно повтора — любой другой момент в прошлом по-прежнему `ErrDueDateInPast`. Сценарий отличает одно от другого не сам, а спрашивая домен (`Task.HasDueDateAt`): сравнение сроков — доменное правило. На стороне `app` это делает `resolveDueDate`, и для существующей задачи звать надо именно его, а не `parseDueDate`, где проверка безусловна.

**События** копятся в агрегате и забираются через `PullEvents()`, который опустошает буфер. Неуспешная операция событий не порождает. Имена событий — часть публичного контракта, менять их так же болезненно, как схему таблицы.

**Граница с хранилищем — `Snapshot()` / `ReconstituteTask()`.** Восстановление не порождает событий и намеренно **не применяет инварианты создания**: задача с просроченным сроком законно лежит в хранилище и обязана оттуда подняться. Не сводить `ReconstituteTask` к вызову `NewTask` — это разные операции.

**У срока есть своя фабрика восстановления — `ReconstituteDueDate`, и она одна такая.** Хранилище в памяти держало доменные значения как есть и ничего не пересоздавало; хранилище на Postgres собирает их из колонок заново, и обычная `NewDueDate(at, now)` отвергла бы просроченный срок — то есть заперла бы просроченную задачу в базе. Исключение сделано именно сроку, потому что его правило задано относительно «сейчас» и кругового пути через хранилище не переживает; заголовок, описание, статус и приоритет от времени не зависят и восстанавливаются обычными фабриками, которые их проверяют. Проверяется в `ReconstituteDueDate` единственное, что осталось: что момент вообще задан (`ErrInvalidDueDate`).

**Указатели через границу агрегата всегда копируются** через `clonePtr[T]`. `*DueDate` и `*time.Time` кодируют необязательность; присваивание структуры в Go копирует указатель, а не значение, поэтому снимок или событие иначе дают доступ к состоянию задачи в обход её методов.

### Application-слой

**`TaskService` ничего не решает.** Сценарий разбирает ввод в значимые объекты, поднимает агрегат, проверяет права, вызывает доменные методы, сохраняет и публикует события. Обычно метод ровно один; исключение — `UpdateTask`, применяющий несколько полей за одну запись (мутации копятся в агрегате, поэтому уезжает либо вся команда, либо ничего). Ни одно доменное правило здесь не дублируется и не перепроверяется: если сценарию хочется заглянуть в статус или сравнить срок — правило живёт не там, где должно.

**Команды несут сырые строки** (`commands.go`). Разбор в `todo.NewTitle`, `todo.ParseTaskID` и прочие фабрики — работа сценария, поэтому HTTP-слой остаётся тупым и о домене не знает. Разбирается всё до `load`: негодная команда не должна стоить чтения. Единственное исключение — срок, которому нужен тот же «сейчас», что увидит домен, поэтому он разбирается внутри мутатора и платит лишним чтением. Асимметрия сознательная и зафиксирована в тестах полем `wantReads` — «выравнивать» её не надо.

**Мутирующие сценарии собраны из одного хелпера** `mutate(ctx, taskID, ownerID, fn)` (`service.go`) — тот же приём, что `apply` в домене. Он делает четыре обязательных шага: `load` (подъём задачи со сверкой владельца), вызов домена, `repo.Save`, публикация. Новый сценарий писать по этому образцу; собственные поля разбирать до вызова `mutate`, а внутри — один вызов домена. Вручную повторять эти шаги нельзя: так теряются проверка владельца и публикация.

**Команда, ничего не изменившая, до записи не доходит.** После вызова домена `mutate` сверяет `task.Version()` с версией подъёма и на совпадении выходит с `nil`. Версию двигает только `apply`, общий хвост любой состоявшейся мутации, поэтому «версия та же» — это ровно «не произошло ничего». Дело не в лишней записи: она сверяется с версией, и чужая правка, случившаяся между `Get` и `Save`, вернула бы вызывающему `ErrVersionConflict` за изменение, которого он не делал. Доменное правило сценарий при этом не дублирует — что считать изменением, решает агрегат, здесь только читается его версия.

**Авторизация — здесь, а не в домене.** `Task` хранит `OwnerID` как идентичность и ни с чем его не сравнивает. Сопоставление владельца задачи с тем, кто её трогает, живёт в одном месте — `load(ctx, taskID, ownerID)` (`service.go`): разбор идентификаторов, `repo.Get`, сверка прав. Через него идут и `mutate`, и читающий `GetTask`, и обязан идти любой новый сценарий, работающий с существующей задачей. Пока подъём был расписан в обоих местах, следующий читающий сценарий списывался бы с `GetTask` — и однажды списался бы без проверки владельца.

**Чужая задача неотличима от несуществующей.** Отказ по владельцу возвращает `ErrTaskNotFound`, отдельной ошибки «нельзя» в контракте нет и заводить её не надо: она сообщала бы постороннему, что задача с таким идентификатором существует, и перебор превращался бы в разведку. Причина отказа остаётся в тексте ошибки — для человека, читающего лог, но не для `errors.Is`. Транспорту в итоге не нужно помнить про маскировку 403 в 404.

**Пустой приоритет трактуется по-разному** и это осознанно: в `CreateTaskCommand` пустая строка — обычный приоритет (нулевое значение `todo.Priority` осмысленно), в `ChangePriorityCommand` — ошибка, потому что команда «сменить приоритет неизвестно на какой» содержания не имеет.

**Порты** — `Repository`, `UnitOfWork` (вместе с `Tx`, `Outbox` и `IdempotencyStore`) и `Clock` (`ports.go`). Интерфейс объявляется у потребителя, а не у реализации: часы нужны только сценариям, поэтому и порт их.

**Изменения идут через единицу работы, чтения — мимо неё.** `TaskService` держит `uow` для записи и `repo` для чтения. Задача, события о ней и ключ идемпотентности обязаны записаться вместе, а прочитать задачу можно и без транзакции: читающий сценарий не пишет, не двигает версию и событий не порождает, а `BEGIN`/`COMMIT` ради одного `SELECT` стоят дороже, чем дают.

**Слово «транзакция» в сценарии не звучит, и это намеренно.** Порт `UnitOfWork` обещает неделимость, а чем она достигнута — транзакцией базы, снимком карты в памяти или чем-то третьим — дело реализации. `Tx` заведён отдельным типом, а не парой аргументов колбэка: список того, что пишется вместе, растёт (сначала очередь, потом ключи), и дописывание к нему не должно переписывать все вызовы.

**Подъём принимает хранилище параметром.** `load(ctx, repo, id, owner)` зовут и изменение (с `tx.Tasks()`), и чтение (с `s.repo`), поэтому проверка владельца по-прежнему живёт в одном месте. Идентификаторы разбираются раньше — в `parseIdentity`, до открытия работы: негодная команда не должна стоить ни чтения, ни начатой транзакции.

**Версия подъёма живёт на границе, а не в домене.** `Get` возвращает `(task, loadedVersion, err)`, `Save` принимает `loadedVersion` обратно; сценарий это число не вычисляет, а переносит. «Откуда взялся этот объект в памяти» — вопрос хранилища: доменное поле, которое объясняется только через хранилище, доменным не является. Пробовали держать его в агрегате (`Task.loadedVersion`) — пришлось объяснять поле через базу и отдельно оговаривать, что сохранённый агрегат нельзя сохранить повторно, потому что он не узнаёт о собственной записи.

**Сверяться нужно именно с версией подъёма.** Выводить ожидаемую версию из сохраняемой (`stored+1 == incoming`) нельзя: писатель, накопивший две мутации, так молча затирает чужую запись, сделанную между его `Get` и `Save`. Это уже случалось — правило «на единицу больше» продержалось один заход ревью и было поймано только внешней проверкой. Число мутаций между `Get` и `Save` не ограничено: «создать, начать, записать один раз» законно и для вставки, и для обновления. Версию ведёт агрегат, хранилище её не назначает.

**`loadedVersion == 0` значит «не поднимал», а не «поднял нулевую версию».** Версия живой задачи всегда не меньше единицы, поэтому нуль однозначен, и в `switch` реализации ветка про занятое место обязана стоять раньше общей сверки версий. Стоя последней, она недостижима: сверка перехватывает случай первой и объясняет повторную вставку расхождением номеров вместо того, что произошло на самом деле. Ошибка при этом та же (`ErrVersionConflict`), расходятся только тексты — но текст ошибки читают в логе, когда всё уже сломалось.

**События не публикуются, а кладутся в очередь рядом с задачей.** `tx.Outbox().Add(task.PullEvents())` идёт в той же работе, что и `Save`, поэтому «задача изменилась» и «об изменении рассказали» — один факт, а не два, из которых второй может не случиться. Доставку из очереди ведёт отдельный механизм (`internal/infra/outbox`), и сценарий о нём не знает: он не выбирает, во что публикует, и не платит за это временем ответа.

**Состояния «записано, но не доставлено» больше не существует.** Прежде отказ публикатора возвращался как `*EventDeliveryError` — запись состоялась, событие потерялось, и вызывающий обязан был различать эти беды. Теперь отказ очереди откатывает и задачу: рассказать об изменении нечем — значит изменения не было. Вместе с этим ушли `EventDeliveryError`, `ErrEventDeliveryFailed`, порт `EventPublisher` и разбор отказа доставки в транспорте.

**Отмена запроса до фиксации отменяет всё.** Раньше публикация шла с `context.WithoutCancel(ctx)`: задача уже была записана, и рассказать о ней следовало независимо от клиента. С очередью эта забота исчезла — рассказ пишется той же транзакцией, что и изменение, поэтому отмена посреди работы просто откатывает её целиком. Сценарий контекст сам не проверяет: отмена всё равно ловится тем, кто в этот момент работает.

**`POST /tasks` идемпотентен по ключу — если клиент его прислал.** Пустой ключ означает прежнее поведение: требовать ключ ото всех значило бы сломать клиентов, которые про него не знают. С ключом сценарий сперва занимает его (`tx.Keys().Reserve`) в той же работе, и повтор возвращает идентификатор задачи, созданной первым запросом, ничего не записывая.

**Отпечаток запроса считается по разобранным значениям, а не по телу.** Так он одинаков для любого транспорта, а запросы, отличающиеся лишними пробелами в заголовке, домен уже свёл к одному — значит и повтором они считаются правильно. Ключ без отпечатка защищал бы только от честного повтора: клиент, пославший с тем же ключом другую задачу, получил бы чужой идентификатор и решил, что создал не то, что создал. Такой случай — `ErrIdempotencyKeyReused`.

**Уборка старых ключей не сделана, и это записано сознательно.** Таблица ключей растёт вместе с числом запросов, и рано или поздно ей нужен либо срок хранения, либо фоновая чистка. И то и другое имеет смысл делать вместе с планировщиком (пункт 19 плана): заводить ради одной таблицы отдельный фоновый процесс сейчас — городить механизм, который через пункт придётся переписывать.

**Чтение отделено от изменения.** `GetTaskQuery` → `TaskView` (`queries.go`): плоское строковое представление из снимка, агрегат наружу не отдаётся. Чтение идёт мимо `mutate` — оно не порождает событий, не двигает версию и не нуждается в блокировке. Списки и фильтры, когда понадобятся, — отдельным портом запросов, а не расширением `Repository`.

**Необязательность выражается типом, а не флагом.** В `UpdateTaskCommand` все поля — указатели: `nil` значит «не менять», а не «поставить пустое». У срока три состояния, поэтому он `*DueDateUpdate`: `nil` — не трогать, пустая структура — снять, с `At` — назначить. Флаг `ClearDueDate` рядом с указателем дал бы то же самое, но позволил бы выразить противоречие «снять и назначить сразу»; здесь оно непредставимо.

**Гарантия доставки — at-least-once, и это условие задачи, а не недоделка.** Между отправкой сообщения и отметкой о ней лежит окно, в котором падение процесса означает повторную отправку: подтверждение получателя и отметка в базе — две записи в двух разных местах, и свести их в одну нечем. Поэтому дедупликация — обязанность получателя.

### Хранилище на Postgres

`internal/infra/postgres`: `repository.go` — реализация порта, `rows.go` — отображение снимка на колонки, `pool.go` — пул и сроки, `migrations.go` плюс каталог `migrations` — схема.

**Порт не изменился ни на букву.** `UPDATE … WHERE id = $1 AND version = $2` — это ровно сверка с версией подъёма, которую порт требовал и от хранилища в памяти. Поэтому `apptest.RepositoryContract` стал готовой красной фазой для этой реализации и здесь впервые проверяет параллельность всерьёз: до сих пор конкурентные подтесты сталкивались на мьютексе внутри процесса, а теперь сталкиваются в базе, где оптимистичную блокировку считает она сама.

**Оптимистичную блокировку считает база, а не код.** Вставка — `INSERT … ON CONFLICT (id) DO NOTHING`, обновление — `UPDATE … WHERE id = @id AND version = @loaded_version`. Ноль затронутых строк означает конфликт, и вклиниться между сверкой и записью нечему: это один запрос. Слить их в `UPSERT` нельзя — тогда вставка затирала бы чужую задачу.

**Связь SQL со значениями именная, а не позиционная, и это исправление, а не украшение.** Сначала было как обычно: константа со списком колонок, срез значений в том же порядке, срез указателей для `Scan` и `$1…$12`, посчитанные руками. Хрупкость здесь не теоретическая — `title` и `description` оба `text` и стоят рядом, поэтому перестановка двух аргументов компилировалась бы, выполнялась бы и писала описание в заголовок; ловил это только контракт, потому что он сверяет оба поля. Теперь чтение идёт через `pgx.RowToStructByName` по тегам `db`, а запись — через `pgx.StrictNamedArgs`, и добавление колонки не требует ни одного номера. **Строгий вариант обязателен:** обычный `NamedArgs` молча подставляет `NULL` вместо ключа, которого не нашёл, — для `NOT NULL` это ловит база, а для необязательных колонок не ловит никто, и опечатка в `due_date` просто теряла бы срок. Измерено: с обычным `NamedArgs` тест сказал «срок потерян», база не возразила ни словом. Строгий отвергает и недостающий параметр, и лишний, ещё до похода в базу.

**Три случая конфликта база одним запросом не различает.** «Место занято», «задачи больше нет» и «версии разошлись» одинаково дают ноль строк, поэтому за нулём идёт уточняющий `SELECT version` — только ради текста ошибки, который читают в логе, когда уже всё сломалось. На решение он не влияет (отказ случился раньше) и на горячий путь не попадает: делается только на конфликте. Ответ может успеть устареть, и это не беда — он описывает обстановку, а не исход.

**Идентификатор хранится как `text`.** `TaskID` — 32 шестнадцатеричные цифры без дефисов, а тип `uuid` вернул бы их с дефисами, то есть в форме, которую `ParseTaskID` не примет. Приводить туда-обратно значило бы поселить в идентичности домена заботу хранилища. Длину сторожит `CHECK`.

**Статус и приоритет — `text` без `CHECK` на значения.** Список статусов живёт в `statusNames`, приоритетов — в `priorityNames`, и у каждого правила ровно один носитель. `CHECK` в схеме стал бы вторым и разошёлся бы с первым молча: новый статус добавили бы одной строкой в домене, а база отвергала бы его при записи. Неизвестное значение ловит `ParseStatus` на подъёме — и ловит по-настоящему: строку в базе мог написать кто угодно, в отличие от карты в памяти, куда попадают только снимки живых агрегатов.

**Порча строки — это 500, а не 400, и следит за этим хранилище.** Фабрики домена отвечают одними и теми же сентинелями и на негодный ввод клиента, и на негодную строку в базе, а `statusFor` перечисляет `ErrUnknownStatus`, `ErrInvalidTaskID`, `ErrEmptyTitle` и прочих среди четырёхсотых — они для того и заведены. Пропусти хранилище доменную ошибку как есть, и `GET /tasks/{id}` по испорченной строке ответил бы «bad request» на безупречный запрос: клиент чинил бы то, что чинить не может, а авария не попала бы ни в одну тревогу по пятисоткам. Поэтому отказ фабрики на подъёме переклассифицируется в `errCorruptRow`, а доменная ошибка уезжает подробностью в скобках — текст для лога сохраняется, цепочка для `errors.Is` обрывается. Различить два случая может только та сторона, которая знает происхождение строки, а знает его одно хранилище.

**Точность времени согласована между часами и базой.** `timestamptz` хранит микросекунды, `time.Now()` даёт наносекунды, и круговой путь через базу перестал бы быть тождественным — причём заметно это стало бы не в контракте (там константы в целых секундах), а на живом сервере. Поэтому `SystemClock.Now()` усекает время до микросекунды: часы и хранилище — обе инфраструктура, и договориться о разрешающей способности они обязаны между собой, а не за счёт домена, который сравнивает моменты через `Equal` и вправе ждать равенства. На чтении моменты нормализуются в UTC: pgx отдаёт их в зоне сессии.

**Соединению закрыты все фазы**, по той же логике, по которой закрыты фазы HTTP-соединения: `statement_timeout` — сам запрос, `idle_in_transaction_session_timeout` — брошенная открытой транзакция, которая держит блокировки и не даёт вакууму убирать мёртвые версии строк, `ConnectTimeout` — подключение к недоступной базе, плюс пределы пула. Сроки ставятся параметрами сессии, а не обёрткой каждого запроса контекстом: так они действуют и на то, что запрос делает уже внутри базы, и на код, который забыли обернуть. **Сроки на сам запрос достаются боевому пулу, но не мигратору** (`limitQueries` зовётся из `Open`, но не из `openSQLDB`): миграция законно идёт долго — индекс на большой таблице строится минутами, — и пятисекундный `statement_timeout` оборвал бы её на середине. Общими у них остаются `ConnectTimeout` и пределы пула.

**Задача, её события и ключ пишутся одной транзакцией** (`tx.go`). `UnitOfWork.Do` открывает её, отдаёт работе `txScope` и фиксирует результат; откат стоит в `defer`, потому что случиться он обязан на любом выходе — включая панику. Хранилища параметризованы исполнителем запросов (`db`: и пул, и транзакция), чтобы SQL не раздваивался на «внутри транзакции» и «снаружи»: вторая версия каждого запроса однажды отстала бы от первой.

**Очередь событий — таблица `outbox`, а уведомление — только побудка** (`outbox.go`, `queue.go`). `NOTIFY` уходит в той же транзакции и без полезной нагрузки: данные лежат в строке, а уведомление говорит лишь «в очереди что-то есть». Так потолок Postgres в 8000 байт не мешает, схлопывание одинаковых уведомлений внутри транзакции работает в нашу пользу (на любое число событий доставщик будится один раз), а главное — потеря уведомления не означает потери события. Одним `NOTIFY` без таблицы обойтись нельзя: его получают только сессии, слушающие в момент фиксации, он не пишется в WAL, не переживает перезапуск базы и не приезжает на реплику, то есть даёт at-most-once — ровно то, от чего outbox и защищает.

**Выборка идёт под `FOR UPDATE SKIP LOCKED`.** Строки, взятые одним доставщиком, другой пропускает, а не ждёт на них: без `SKIP LOCKED` второй проснулся бы ровно затем, чтобы обнаружить их отправленными. Отметка о доставке фиксируется той же транзакцией, что и изъятие — между «взял» и «отметил» не должно быть окна, в котором сообщение снова видно. Отказ доставки фиксируется тоже, но вместо отметки: сообщение остаётся в очереди, а `attempts` и `last_error` объясняют, почему она не пустеет. Пока идёт доставка, транзакция держит строки, и это осознанная цена — зависшего получателя обрубит `idle_in_transaction_session_timeout`, а не унесёт очередь с собой.

**Поля событий раскладываются в JSON руками** (`events.go`). `encoding/json` домену не помощник: значимые объекты держат своё в закрытых полях, и обычная сериализация выдала бы `{}` вместо заголовка. Незнакомое событие — ошибка, а не пустая нагрузка: новое событие, о котором забыли в мапере, иначе уехало бы пустышкой и обнаружилось бы у получателя, когда чинить поздно.

**Ключи идемпотентности защищает уникальный индекс, а не код.** `INSERT … ON CONFLICT (owner_id, key) DO NOTHING`: ноль затронутых строк означает «ключ занят», а чем именно — выясняет следующий запрос. Параллельный повтор ждёт на индексе, пока первый запрос не зафиксируется, и после этого читает готовый ответ — замок здесь сама база, и второй, в коде, был бы лишним и неверным. `DO UPDATE` вместо `DO NOTHING` был бы ошибкой: за занятым ключом стоит уже созданная задача, и переписать его значило бы потерять ответ, которого клиент ещё не получил.

**Миграции — отдельная команда, а не шаг при старте.** `cmd/todoer-migrate up|down|status` поверх goose, миграции вшиты через `embed`: на машине выкатки рядом с бинарником нет исходников. Приложение схему не двигает и сверяет её при старте (`EnsureSchema`): база отстала — запуск отменяется, потому что код обращался бы к колонкам, которых ещё нет. Схема новее ожидаемой пропускается: так выглядит откат кода при накатанных миграциях, и запрещать его значило бы лишить себя отката.

### Доставка событий

**Доставщик отделён от хранилища** (`internal/infra/outbox`): политика доставки не имеет отношения к SQL, и наоборот. Пакет держит `Message`, порты `Queue`, `Publisher` и `Waiter` — все объявлены у потребителя, то есть у самого доставщика, — и цикл `Relay.Run`. Реализации `Queue` и `Waiter` живут в `postgres`, а сам доставщик проверяется на поддельных и базы не требует.

**Доставщик работает с плоским сообщением, а не с доменным событием, и иначе нельзя.** События конструирует только агрегат: `eventMeta` неэкспортирована, фабрик наружу нет, и собрать `todo.DomainEvent` обратно из строки нечем. Отсюда же исчез порт `EventPublisher` в `app` — публиковать доменные события стало некому и незачем.

**Выгребание идёт до ожидания, а не после.** Уведомления, случившиеся, пока доставщика не было, никто не повторит, поэтому первый заход обязан быть безусловным — и после каждого переподключения тоже. Отсюда же правило слушателя: только что созданная подписка не ждёт ни секунды, а возвращает управление сразу, заставляя перечитать очередь уже подписанным. Без этого событие, созданное сразу после запуска, ждало бы страховочного опроса — минуту вместо миллисекунд; ровно это и случилось при первом прогоне сквозного теста.

**Страховочный опрос остаётся** (`pollInterval`, минута). Уведомление ненадёжно по своей природе, и без опроса «не потерять» держалось бы на нём одном. Редкий: пропущенное уведомление тогда стоит задержки, а не потери.

**Соединение слушателя — своё, мимо пула.** Пул закрывает соединения по `MaxConnIdleTime` и `MaxConnLifetime`, а закрытое соединение молча теряет `LISTEN`: доставщик остался бы ждать уведомлений, которых ему больше никто не пришлёт. Сроков боевого пула на нём тоже нет — ожидание уведомления не запрос, и `statement_timeout` ему ни к чему. Истёкший срок ожидания соединение переживает: для pgx таймаут не фатален, в отличие от всякой другой ошибки чтения, — а вот на ней соединение закрывается, чтобы следующее ожидание начиналось с подключения.

**Публикатор пока заглушечный** (`outbox.NopPublisher`). Шины событий нет, и это честная заглушка на её месте: сообщения остаются в таблице с отметкой о доставке, так что теряется не событие, а только его путешествие наружу. Когда шина появится, поменяется ровно эта реализация.

### Транспорт

**Транспортный слой тупой по устройству.** Он разбирает JSON в команды из сырых строк, зовёт ровно один сценарий и переводит его ошибку в код ответа. Доменных типов он не знает: превращение строк в значимые объекты — работа `app`, и перенос её сюда заставил бы второй транспорт дублировать домен. `TaskService` объявлен здесь же (`api.go`), у потребителя: транспорту нужен не весь `*app.TaskService`, а тестам нужен двойник.

**Маршрутизация штатная.** Шаблоны с методом и переменной пути есть в `net/http` с 1.22, поэтому внешний роутер не нужен; несовпадение метода на известном пути мультиплексор сам превращает в 405.

**Владелец приезжает в заголовке `X-Owner-ID`.** Аутентификации пока нет, и это её заглушка: клиент просто называет себя. Когда появится настоящая, заголовок будет читать её middleware, а обработчики останутся прежними — в этом и смысл заголовка вместо префикса в пути: личность в URL утекает в логи, `Referer` и историю браузера, а сменить схему потом можно только сломав все ссылки. Отсутствующий или пустой заголовок — 400, а не 401: схемы аутентификации нет, а 401 обязывает прислать `WWW-Authenticate`.

**Владелец достаётся в `withOwner` и уезжает в обработчик параметром, а не через контекст.** Из контекста обработчик достаёт `any`, и компилятор не обещает ничего: забытая на новом маршруте обёртка дала бы пустого владельца, а отказ приехал бы из фабрик `todo` — после чтения и с другим кодом. Обработчик же с сигнатурой `ownerHandler` (третий параметр — владелец) в `HandleFunc` просто не подставляется: пару «маршрут — владелец» держит компилятор, а не память пишущего. Когда появится настоящая аутентификация, менять придётся только нутро `withOwner` — туда владелец приедет из контекста, куда его положит её middleware.

**Обёрнут каждый маршрут, а не мультиплексор целиком.** Обёртка вокруг мультиплексора встала бы раньше маршрутизации, и запрос к несуществующему пути без заголовка получал бы 400 вместо 404.

**Переходы статуса вынесены в действия, а не в поле `PATCH`:** `POST /tasks/{id}/start|complete|cancel`. Статус живёт в конечном автомате с `transitionMatrix`, и «присвоить статус» — не та операция, которую предлагает домен. Запрещённый переход — 409, а не 400: тот же самый запрос был бы законен, застань он задачу в другом статусе.

**Три действия статуса собраны из одного `changeStatus`.** Тела у этих запросов нет, различаются они одним вызовом сценария (типы команд разные, поля одинаковые — отсюда `statusAction`), а общее — идентификатор из пути, разбор отказа доставки и перечитывание задачи в ответ. Расписывать это трижды нельзя по той же причине, по которой в `app` есть `mutate`.

**`POST /tasks` отвечает 201, `Location` и телом с одним полем — `id`.** Заголовок для того, кто ходит по ссылкам, поле для того, кто разбирает JSON. Задачу целиком тело не несёт и не должно: остальное клиент только что прислал сам, а статус, версию и времена назначает домен — собери мы их из присланного, клиент увидел бы не то, что лежит в хранилище. Кому нужна задача целиком, тот идёт по `Location`.

**Тело запроса ограничено сверху** (`maxBodyBytes`, 64 КиБ, превышение — 413). Транспорт разбирает раньше, чем сценарий проверит длину, поэтому без потолка гигабайтный заголовок сначала целиком оказался бы в памяти и только потом получил бы 400 за длину — несколько таких запросов кладут процесс. Число берётся из доменных пределов (256 рун заголовка, 4096 описания — в худшем случае с экранированием десятки килобайт) с запасом, но константы `todo` сюда не импортируются: это предел провода, а не доменное правило.

**Разбор строгий: `DisallowUnknownFields` и запрет хвоста после документа** (`decodeBody`, `expectEOF`). Опечатка в имени поля иначе отвечает успехом, ничего не изменив, и клиенту неоткуда узнать, что его правку выбросили; второй документ в теле молча пропадал бы, а клиент считал бы принятыми оба.

**`PATCH` и действия статуса отвечают обновлённой задачей**, а это лишний `GetTask` после записи (`respondTask`): мутирующие сценарии возвращают только ошибку. Отказ этого чтения — 500, и ошибку сценария сюда пускать нельзя: запись состоялась, задача есть, и 404 был бы враньём.

**Ключ идемпотентности приезжает заголовком `Idempotency-Key` и уезжает в команду как есть.** Заголовком, а не полем тела: это свойство доставки запроса, а не часть задачи, и попади он в тело — уехал бы в отпечаток самого себя. Необязательный: есть ключ — повтор вернёт ту же задачу, нет — поведение прежнее; требовать его ото всех значило бы сломать клиентов, которые про него не знают. Про повторы транспорт ничего не решает — отличать повтор от нового запроса работа сценария, а переиспользованный ключ становится 409: сам запрос безупречен, и с другим ключом он прошёл бы.

**Разбора отказа доставки больше нет.** Прежде транспорт ловил `*EventDeliveryError` и отвечал на него успехом: задача записана, события не ушли, а 5xx позвал бы клиента повторить уже состоявшуюся запись. С outbox'ом такого состояния не существует — событие пишется вместе с задачей, — и `written` исчез вместе с ним.

**Тексты ошибок наружу не уезжают.** Известные сентинели переводятся в коды в `statusFor`, текст ответа выводится из кода (`statusText`), а неопознанная ошибка — 500 с общим текстом: в ней может оказаться имя таблицы, путь или адрес соседнего сервиса. Сентинели в `statusFor` перечислены поимённо, а не сведены к правилу «всё из `todo` — 400»: конфликт состояния приходит оттуда же, и такое правило отвечало бы на него 400 вместо 409.

**Необязательность переживает провод — там, где состояний три.** У заголовка, описания и приоритета в `PATCH` их два (поля нет — не трогать, есть значение — назначить), и обычного указателя довольно: снимать их нечем и не за чем — пустое описание снимается пустой строкой, а заголовок и приоритет у задачи есть всегда. Присланный им `null` от отсутствия поля неотличим и значит «не трогать». Три состояния только у срока, и вот их `encoding/json` сам не различает: и отсутствие, и `null` дают нулевой указатель. Отсюда `json.RawMessage` у одного лишь срока — сырой кусок хранит разницу, а `parseDueDateUpdate` раскладывает его в три состояния `app.DueDateUpdate`. Вложенная структура вместо этого не подходит дважды: она требует другого формата на проводе (`{"due_date":{"at":…}}` вместо строки) и всё равно не различает отсутствие и `null` — как и `**time.Time`, проверено. В ответах необязательные поля уезжают как `null`, а не пропадают: клиент должен видеть разницу между «срока нет» и «поле не пришло».

**Файл `api.go` разложен сверху вниз по ходу запроса:** сборка и маршруты, обработчики, формы запросов и ответов на проводе, общий хвост записи и перевод ошибок в коды.

### Композиционный корень

**Команда поднимает HTTP-сервер и живёт, пока её не остановят.** Сигнал приходит отменой контекста (`signal.NotifyContext` на `os.Interrupt` и `SIGTERM`), поэтому остановка по Ctrl+C и остановка по отмене — один путь, а не два разных. `run(ctx, out, addr)` вынесен отдельно от `main`, чтобы его мог водить тест: адрес приезжает параметром, а не из окружения, вывод идёт в `out`, а не в `os.Stdout`. Отмена — штатное завершение, поэтому `run` возвращает `nil`.

**Обработчик сигналов снимается сразу после отмены** (`restoreSignalsOnCancel`), а не в конце `main`. Первый сигнал запускает остановку длиной до `shutdownTimeout`, и всё это время обработчик продолжал бы ловить сигналы — второй Ctrl+C оператора, которому надоело ждать, не делал бы ничего, потому что контекст уже отменён. Сняв обработчик, мы возвращаем второму сигналу его обычное действие: убить процесс.

**Слушатель открывается до `Serve`.** Иначе занятый порт стал бы не ошибкой запуска, а тихой смертью в горутине. Он же сообщает настоящий адрес: с портом `0` его выбирает ядро, и узнать его можно только из вывода — оттуда же, откуда его узнаёт человек, запустивший команду.

**Доставщик событий работает горутиной рядом с сервером.** Своя команда ему пока не нужна: выкатка одна, процесс один, — а код доставки отделён и переедет, когда понадобится. Останавливается он своей отменой, производной от `ctx`, и вот почему: `run` умеет выйти рано — например, на занятом порту, — когда внешний контекст ещё жив, и без собственной отмены горутина пережила бы функцию, которая её завела, а ожидание её завершения не кончилось бы никогда. Это не теория: именно так тест «занятый адрес — ошибка, а не паника» и повис. Отмена и ожидание стоят в одном `defer`, чтобы порядок нельзя было перепутать, а соединение слушателя закрывается после того, как доставщик остановился.

**Остановка ждёт текущие запросы.** `Shutdown` идёт на контексте от `context.WithoutCancel(ctx)` с таймаутом: `ctx` к этому моменту уже отменён, и передать его как есть значило бы оборвать ровно те запросы, которые мы собрались дождаться. Таймаут нужен с другой стороны: висящий бесконечно процесс хуже оборванного ответа.

**Закрыты все фазы соединения, а не одни заголовки** (`newServer`). Нулевой таймаут у `http.Server` значит «ждать вечно», а вечно ждущее соединение — самый дешёвый отказ в обслуживании из возможных: атакующему он не стоит ничего. `ReadHeaderTimeout` — молчащее соединение без заголовков; `ReadTimeout` — весь запрос, то есть и тело, сочащееся по байту; `WriteTimeout` — работа обработчика и отправка ответа, включая клиента, который не читает; `IdleTimeout` — сон между запросами в keep-alive. Сборка сервера вынесена отдельной функцией, чтобы тест мог убедиться, что ни один из четырёх не остался нулевым: пропажу таймаута иначе видно только под нагрузкой, когда чинить уже поздно.

**Адрес — из `TODOER_ADDR`, иначе `:8080`.** Порт в коде не зашит: занятый порт на машине разработчика не повод править исходники. Пустая переменная равна отсутствующей — пробелы не адрес.

**Адрес базы берётся из `TODOER_DATABASE_URL`, и умолчания у него нет.** Пустая переменная — отказ запуска, а не тихий переход на хранение в памяти: приложение, «работающее» ровно до первого перезапуска, хуже не запустившегося. База открывается прежде слушателя и по той же причине, по которой слушатель открывается до `Serve`: недоступная база должна быть ошибкой запуска, а не потоком пятисоток на каждом запросе. Публикатор по-прежнему заглушечный — шины событий ещё нет, а `nil` вместо него запрещён конструктором.

## Ошибки

**`%w` всегда последний, контекст — слева.** Обёртка описывает, что делали, причина остаётся в хвосте, и цепочка читается слева направо от внешнего действия к корню:

```
app: mutate task e0443c5f…: todo: task is already completed
app: build task service (task repository): app: missing dependency
todo: parse task id (length 3, want 32): todo: invalid task id
```

Сентинель — такая же причина, как чужая ошибка, поэтому `fmt.Errorf("%w: подробности", ErrX)` не писать: на `errors.Is` позиция `%w` не влияет вообще, так что выбор чисто про читаемость, а перевёрнутый порядок ломает цепочку. Подробности идут в скобках перед двоеточием: `fmt.Errorf("infra: save task %s (loaded version %d, stored version %d): %w", …, app.ErrVersionConflict)`. Текст перед двоеточием называет операцию и не пересказывает сентинель, иначе выходит «task not found: задача не найдена». Единственное исключение — `ParseTaskID`, где `%w: %w` несёт сразу классификацию и причину от `hex`.

**Сентинель заводится тогда, и только тогда, когда кто-то напишет по нему `errors.Is`.** Если ветвиться по ошибке некому, это не сентинель, а сообщение, которому зачем-то дали имя пакетного уровня; такую ошибку порождают на месте через `fmt.Errorf`. Доказательство необходимости в этом проекте видно глазами: `statusFor` (`api.go`) выбирает между 400, 404, 409 и 408 — двенадцать сентинелей существуют ровно потому, что этот выбор надо сделать. А `postgres: parse connection string` ветвления не порождает никогда: ответ на него один — 500 и строка в лог, поэтому он и написан на месте.

Уточнения к этому правилу:

- **Потребитель — машина, а не человек.** Читателю лога нужен текст, ветвящемуся — опознаваемость. Как только в сентинель просачивается подробность, он перестаёт быть сравнимым: подробности идут в скобках перед двоеточием, сентинель отвечает только на «что за класс события».
- **Экспортированный сентинель — это API навсегда.** Стоит он не строчки `var`, а того, что его удаление ломает чужой код. Отсюда неэкспортированный сентинель как полноценная середина: он даёт сравнимость внутри пакета и его тестов, а выбросить его можно в любой день (`errNilTask`, `errUsage`).
- **Тест — законный потребитель, но только когда проверяет чужое обещание.** `errors.Is(err, app.ErrVersionConflict)` в наборе контракта образцов: порт обещает сентинель, а тексты в контракт не входят, и три реализации формулируют их по-своему. Если же по сентинелю ветвится только тест, а ни один порт его не обещает и в бою реагировать на него некому, — требование выдумал тест.
- **Один сентинель на условие, а не на место в коде.** В хранилище три ситуации конфликта — место занято, задачи больше нет, версии разошлись, — и один `ErrVersionConflict` на все три, потому что решение вызывающего во всех трёх одинаково: 409. Различаются они текстом, который читают в логе.
- **Нужны данные, а не опознание, — это уже тип, а не сентинель.** Порядок эскалации: текст на месте → сентинель → тип с полями. В этом коде до третьей ступени пока не дошло: `EventDeliveryError` был единственным таким типом и уехал вместе с синхронной публикацией — недоставленных событий, которые надо было вынести наружу в ошибке, больше не бывает, они лежат в очереди.
- **Сначала переиспользовать, потом изобретать.** Хранилище на Postgres возвращает `app.ErrTaskNotFound` и `app.ErrVersionConflict` — чужие сентинели, — и ровно поэтому подставляется в порт как своё. Заведи оно свои, транспорту пришлось бы знать про инфраструктуру.

Практический признак лишнего: единственные ссылки на сентинель — его объявление и один `fmt.Errorf`. Измеряется одной командой — сколько раз по нему написан `errors.Is` во всём дереве, включая тесты. Так поймались двое собственных: `errNoMigrations` и `errBadMigrationName` не имели ни одного потребителя нигде и свёрнуты в текст на месте, причём один из них заодно перестал пересказывать сам себя (`read embedded migrations: no embedded migrations`), а второй начал показывать настоящую причину от `strconv` вместо собственной формулировки.

**Тексты ошибок — по-английски, в нижнем регистре, без точки в конце и без «failed to».** Это относится и к сентинелям, и к обёрткам, и к тестовым двойникам: ошибки читают логи и поиск по трекеру, а не человек за спиной. Комментарии, названия подтестов и диагностика в `t.Errorf` остаются русскими — их аудитория другая.

**Префикс пакета** (`todo:`, `app:`, `infra:`) ставится в сентинелях и в обёртках, порождающих ошибку на месте. Пробрасывая чужую ошибку без своего контекста, префикс не добавлять — он уже есть внутри.

## Тесты

Живут в `package todo_test`, `package app_test`, `package httpapi_test` и `package postgres_test` — все слои проверяются через публичный API, как их будет использовать вызывающая сторона.

**Таблицы операций общие.** `fieldMutations()` и `statusMutations()` в `task_test.go`, `taskMutations()` в `internal/app/service_test.go` перечисляют мутации один раз, и их переиспользуют все тесты, которые обходят операции. Добавляя мутатор в `Task` или сценарий в `TaskService`, добавить его в соответствующую таблицу — тогда он автоматически попадёт под проверки терминальных статусов, `updatedAt`, авторизации и конфликта версий.

**Доменные значения для тестов собирает `internal/domain/todo/todotest`** — те же фабрики `todo`, но с падением теста вместо возвращаемой ошибки: `MustTitle`, `MustDescription`, `MustTaskID`, `MustOwnerID`, `MustDueDate`, `MustReconstituteDueDate`, плюс `NewTask` (типовая задача со сроком через сутки) и `EventNames`. Пакет обычный, а не тестовый, — по той же причине, что `apptest` и `pgtest`: его импортируют тесты пяти разных пакетов, а из файлов с суффиксом `_test` импортировать нечего. До него этот набор был скопирован в каждый из них, и правка одной доменной фабрики стоила пяти одинаковых правок.

**Опорные моменты времени в `todotest` не переехали и не должны.** «Сейчас» приезжает в `MustDueDate` и `NewTask` параметром: у каждого пакета своя точка отсчёта, а общая изменяемая переменная времени — это состояние на весь тестовый бинарник ради экономии одной строки. Своё `testNow` каждый пакет объявляет сам; в домене от него же считаются `testLater`, `testMuchLater`, `testEvenLater`, `testTomorrowAt`. Остаются локальными и сборщики, у которых своя работа: `newTestTask`/`newTestTaskWithDueDate` в домене (им нужна задача именно без срока), `seedTask` в сценариях (доводит задачу до статуса и кладёт в хранилище), `mustSave`/`mustGet`/`mustRename` в наборе контракта (это инструмент набора, а не доменные фабрики), `mustTaskID` в транспорте (разбирает фиксированный `testTaskID`, а не создаёт новый).

**Подставные зависимости app-слоя** — в `internal/app/fakes_test.go`. `fakeRepository` хранит именно снимки, а не указатели на агрегат: иначе сценарий, забывший `Save`, «сохранял» бы изменения через общий объект и тест этого не заметил бы. Правила блокировки в двойнике повторяют настоящие: упрощённый двойник перестаёт ловить то, на чём споткнётся оригинал, — на этом уже терялась дыра с потерянным обновлением.

**Совпадение реализаций порта проверяется набором, а не глазами.** Наборов теперь три, и все живут в `internal/app/apptest`: `RepositoryContract` (хранилище задач), `UnitOfWorkContract` (единица работы) и `IdempotencyContract` (ключи). Реализаций у каждого по две — двойник из тестов сценариев и Postgres, — и разъезжаются они молча: двойник однажды панике́й отвечал там, где порт требует ошибку. Прогоняются оба через `internal/app/contract_test.go` и `internal/infra/postgres/contract_test.go`.

**Набор единицы работы проверяет ровно одно, но крупное: работа фиксируется целиком или не фиксируется вовсе.** Отказ внутри неё не оставляет ни задачи, ни событий; паника — тоже (незавершённая работа не становится завершённой оттого, что вышла необычным путём); конфликт версий доезжает до вызывающего нетронутым. Очередь набор читает не через порт, а через средство осмотра, которое даёт сама реализация (`UnitOfWorkFixture.QueuedEvents`): очередь читает доставщик, и заводить ради теста метод, которым сценарий не пользуется, незачем.

**Набор ключей идемпотентности впервые проверяет замок по-настоящему.** Двойник разводит параллельные повторы мьютексом внутри процесса, а Postgres — уникальным индексом, и подтест «из параллельных повторов побеждает один» на нём значит то же самое, что на живом сервере: восемь одновременных запросов с одним ключом дают ровно одну задачу.

**Доставщик проверяется без базы.** `internal/infra/outbox` тестируется на поддельных очереди, публикаторе и побудке: очередь выгребается до дна, недоставленное остаётся на месте, отказ учитывается попыткой, а очередь, наполненная до запуска, уезжает без всякого уведомления. Реализации `Queue` и `Waiter` проверяются уже на живой базе — там, где есть что блокировать и чем уведомлять. `NOTIFY` при этом не мешает параллельным тестам: каналы уведомлений живут в пределах базы, а `pgtest` выдаёт каждому свою.

**Набор — самая дешёвая часть этой конструкции, а не самая дорогая.** Соблазн «оставить одни контракты» разбирали отдельно и отвергли: набор — один файл, а `contract_test.go` — по два десятка строк каждый. Изменение порта стоит одного набора плюс реализаций; без набора оно стоило бы набора на каждую реализацию, расходящихся поодиночке и молча. Резать нечего и с другой стороны: собственные тесты есть только у хранилища на Postgres, и проверяют они ровно то, чего порт не обещает.

**Сокращать надо было не наборы, а реализации, и `InMemoryTaskRepository` удалён.** После перехода на Postgres боевого потребителя у него не осталось — `cmd/todoer` без `TODOER_DATABASE_URL` не стартует, — а держался он на собственном прогоне контракта и на `TestNewTaskService`. При этом он дословно повторял двойника из тестов сценариев, включая `switch` оптимистичной блокировки с порядком веток: одно правило, записанное дважды, — ровно то, чего в этом проекте быть не должно. Реализаций стало две, и обе живые: одна боевая, другая нужна тестам сценариев ради инъекции отказов и хука перед записью. `TestNewTaskService` собирает сервис на настоящем хранилище — проверка «боевые реализации подходят портам» иначе проверяла бы подставную.

**Хранилищу на Postgres собственные тесты всё же нужны — но только на то, чего порт не обещает** (`internal/infra/postgres/repository_test.go`): просроченный срок поднимается из колонки; момент, выданный часами, переживает круговой путь тождественно, а наносекунды теряются; строка с неизвестным статусом — ошибка подъёма, а не тихий нулевой статус. Ни одну из них двойник или карта в памяти удовлетворить не могут: там нечего портить и нечему усекаться.

**Каждый тест получает свою базу.** `internal/infra/postgres/pgtest` один раз накатывает схему в шаблонную базу, а дальше выдаёт копии через `CREATE DATABASE … TEMPLATE` и удаляет их в `t.Cleanup` с `WITH (FORCE)` — незакрытое соединение иначе оставило бы базу навсегда. Копия готовой схемы обходится дешевле повторного наката миграций, а изоляция получается полной: подтесты контракта не знают друг о друге и общего состояния не переживут. `pgtest.NewEmptyDSN` даёт базу без схемы — тем, кто проверяет сам накат: накатывать миграции на базу, где они уже накатаны, значит проверять идемпотентность, а не накат.

**Разъезжаться реализациям положено, но не в поведении.** Мьютекс против `WHERE version = @loaded_version`, имена полей, префиксы в текстах ошибок, инъекция отказов, хук `beforeSave`, счётчик записей — собственное дело каждой; сводить их к общему коду не надо, иначе средства теста уедут в боевое хранилище. В набор идёт только то, на что вправе рассчитывать вызывающий; тексты ошибок туда не входят — контракт сверяет сентинели через `errors.Is`.

**Новую реализацию любого из портов начинать с подключения набора** — это её готовая красная фаза. Новое обещание порта дописывать в набор, а не в тесты одной реализации: иначе вторая про него не узнает.

**Проверка не должна быть невыполнимой.** Сравнение указателей из двух вызовов `Snapshot()` всегда даёт `false` — снимок клонирует их каждый раз, — поэтому изоляция состояния проверяется поведением: меняем через одну копию, смотрим на другую. Тест, который не может упасть, хуже отсутствующего: он создаёт видимость покрытия. Хук `beforeSave` изображает чужую запись, вклинившуюся между `Get` и `Save`. Часы — `stubClock`, время подставное, как и в домене.

**Транспорт проверяется на двойнике сценариев** (`internal/transport/httpapi/fakes_test.go`), а не на настоящем `TaskService` с хранилищем в памяти. Транспорт отвечает за разбор запроса и перевод ошибки в код, и подставить ему нужную ошибку — единственный способ этот перевод проверить: на живом сервисе половину из них (конфликт версий, отказ доставки, отмену контекста) пришлось бы подстраивать через хранилище, и тест проверял бы не транспорт, а собственную изобретательность. Команды двойник запоминает целиком — разбор запроса в команду тоже работа транспорта. Тело ответа тест разбирает в карту, а не в структуру транспорта: тест, читающий ответ теми же тегами, которыми его писали, пропустил бы опечатку в теге — она сошлась бы сама с собой.

**Тест команды водит настоящий сервер поверх настоящей базы.** `run` поднимается на `127.0.0.1:0`, адрес читается из вывода, задача создаётся и читается обратно обычным `http.Client` — значит слои действительно соединены, а не просто скомпилировались. Отдельный подтест останавливает сервер и поднимает его заново на той же базе: то, ради чего затевался переход на Postgres, хранилище в памяти не прошло бы никогда. Вывод синхронизирован (`syncBuffer`): пишет в него сервер, читает тест, и обычный `bytes.Buffer` здесь ловится `-race`.

Сравнивать моменты времени только через `Equal`/`After`/`Before`. Оператор `==` у `time.Time` сличает внутреннее представление, включая зону и монотонный отсчёт, — на этом уже был баг.
