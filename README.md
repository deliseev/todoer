# ToDoer

## О проекте

`todoer` — учебное приложение управления задачами. Строится снизу вверх: от доменной модели к микросервисной архитектуре. Цель проекта не в готовом продукте, а в отработке TDD и DDD на реальном коде.

**Жёсткие ограничения, заданные владельцем проекта:**

- **Только стандартная библиотека.** Никаких внешних зависимостей — ни для тестов, ни для UUID, ни для чего-либо ещё. `go.mod` обязан оставаться без блока `require`.
- **Строгий TDD.** Сначала падающие тесты, затем реализация. Не писать реализацию, пока тесты на неё не показали красноту.
- **Идентификаторы английские, комментарии и названия подтестов русские.** Диалог с пользователем тоже на русском.
- Идиоматичный Go 1.26 без устаревших конструкций. В частности, указатель на значение — это `new(x)` для любого выражения; самодельные хелперы вида `ptr[T any](v T) *T` были нужны до 1.26 и сейчас лишние.

## Команды

```bash
go test ./...                                    # весь набор
go test ./... -race -count=1                     # обязательно перед сдачей работы
go test ./internal/domain/todo/ -run TestNewTitle -v   # один тест
go test ./... -run 'TestTaskMutations' -v        # группа по регулярке
go vet ./...
gofmt -s -l .                                    # должен молчать; -s ловит несокращённые литералы
```

`gofmt -s -l .` и `go test -race` — не формальность: оба ловили реальные дефекты в этом коде. Прогонять оба перед тем, как объявить работу законченной.

Быстрая сводка по красноте/зелени:

```bash
go test ./... -count=1 -v 2>&1 | grep -cE '^\s*--- PASS'
go test ./... -count=1 -v 2>&1 | grep -cE '^\s*--- FAIL'
```

## Архитектура

Три пакета и команда: `internal/domain/todo` — чистое доменное ядро, оно не знает о хранилищах, транспорте и фреймворках и не должно узнать; `internal/app` — сценарии использования поверх него; `internal/infra` — реализации портов `app` (`InMemoryTaskRepository`, `SystemClock`, `NopPublisher`); `cmd/todoer` — композиционный корень. Особняком стоит `internal/app/apptest` — наборы тестов контракта для портов `app`; в сборку приложения он не входит, но пакет обычный, а не `_test`, потому что его импортируют тесты двух разных пакетов. Зависимости направлены внутрь: `cmd` → `infra` → `app` → `todo`, обратного знания нет ни на одном уровне.

**Слои встречаются только в `cmd/todoer`.** Там и только там инфраструктура подставляется в порты сценариев. Пока нет транспорта, команда прогоняет жизненный цикл одной задачи и печатает результат — дымовая проверка того, что собранное приложение живо; `run(ctx, out)` вынесен отдельно от `main` именно чтобы его можно было проверить тестом.

### Домен

**Агрегат — `Task`, и он один.** Транзакционная граница совпадает с одной задачей. Связи с другими агрегатами хранятся по идентичности (`OwnerID`), а не ссылкой на объект. `TaskList` появится позже отдельным агрегатом, хранящим имя и владельца, но не сами задачи. Это решение принято сознательно ради будущего шардирования и разнесения по сервисам — не переделывать его на «список как контейнер задач» без явной просьбы.

**Время в домен приходит параметром.** Каждый мутирующий метод принимает `now time.Time`. Агрегат никогда не спрашивает время сам и о часах не знает вовсе: порт `Clock` живёт у своего единственного потребителя — в `internal/app/ports.go`, реализация `SystemClock` — в `internal/infra`. Благодаря этому тесты домена работают с обычными константами и не нуждаются в моках.

**Значимые объекты валидны по построению.** `Title`, `Description`, `Priority`, `Status`, `DueDate`, `TaskID`, `OwnerID` — сравнимые структуры с приватными полями, создаются только через фабрики. Агрегат **не должен** перепроверять их содержимое или лезть в приватные поля: единственное, в чём он убеждается, — что вместо объекта не передали нулевое значение (`IsZero()`, `IsValid()`).

**У каждого правила ровно один носитель.** Имена статусов — `statusNames`, имена приоритетов — `priorityNames`, разрешённые переходы — `transitionMatrix`. И `String()`, и `Parse*()` читают одну и ту же таблицу. Добавление статуса или приоритета — правка одной таблицы, а не пяти `switch`.

**Мутаторы `Task` собраны из трёх приватных хелперов** (`task.go`):

- `ensureMutable()` — единственный guard, спрашивает `Status.IsTerminal()`, а не перечисляет статусы сам;
- `apply(now, event)` — обязательные три шага любой успешной мутации: `updatedAt`, `version++`, `append` события;
- `transitionTo(target, now, event)` — то же плюс сверка с `transitionMatrix`.

Новый мутатор писать по этому же образцу и обязательно заканчивать вызовом `apply`. Дублирование этих строк вручную уже приводило к четырём потерянным присваиваниям `updatedAt`.

**Повтор — не мутация.** Перед `apply` мутатор сверяет присланное значение с текущим и на совпадении возвращает `nil`, не трогая ни версию, ни события. Иначе клиент, присылающий форму целиком (а `UpdateTask` — именно такой сценарий), каждым сохранением рассылает «изменилось» по неизменившимся полям и двигает версию, отбирая оптимистичную блокировку у всех остальных: измеряли — PATCH со всеми полями, равными сохранённым, давал `version 1 → 5` и четыре события. Значимые объекты сравнимы, поэтому это `==`; для срока — `DueDate.Equal` (у `time.Time` `==` сличает не момент) и `sameDueDate` для необязательности, где `nil` значит «срока нет», а не «поле пропущено». Добавляя мутатор, добавить его и в `sameValueMutations()` в `task_test.go`.

**В `Reschedule` проверка повтора стоит раньше проверки срока, и порядок содержательный.** Перенос на уже стоящий момент — не перенос, требовать от него будущего не за что; задача с просроченным сроком законно живёт в хранилище, и вернуть ей её же срок — не то же самое, что назначить просроченный. Без этого круг `GetTask` → `UpdateTask` разрывался бы: `TaskView` отдаёт срок наружу, клиент возвращает форму целиком, и у просроченной задачи нельзя было бы изменить даже заголовок. Послабление касается ровно повтора — любой другой момент в прошлом по-прежнему `ErrDueDateInPast`. Сценарий отличает одно от другого не сам, а спрашивая домен (`Task.HasDueDateAt`): сравнение сроков — доменное правило. На стороне `app` это делает `resolveDueDate`, и для существующей задачи звать надо именно его, а не `parseDueDate`, где проверка безусловна.

**События** копятся в агрегате и забираются через `PullEvents()`, который опустошает буфер. Неуспешная операция событий не порождает. Имена событий — часть публичного контракта, менять их так же болезненно, как схему таблицы.

**Граница с хранилищем — `Snapshot()` / `ReconstituteTask()`.** Восстановление не порождает событий и намеренно **не применяет инварианты создания**: задача с просроченным сроком законно лежит в хранилище и обязана оттуда подняться. Не сводить `ReconstituteTask` к вызову `NewTask` — это разные операции.

**Указатели через границу агрегата всегда копируются** через `clonePtr[T]`. `*DueDate` и `*time.Time` кодируют необязательность; присваивание структуры в Go копирует указатель, а не значение, поэтому снимок или событие иначе дают доступ к состоянию задачи в обход её методов.

### Application-слой

**`TaskService` ничего не решает.** Сценарий разбирает ввод в значимые объекты, поднимает агрегат, проверяет права, вызывает доменные методы, сохраняет и публикует события. Обычно метод ровно один; исключение — `UpdateTask`, применяющий несколько полей за одну запись (мутации копятся в агрегате, поэтому уезжает либо вся команда, либо ничего). Ни одно доменное правило здесь не дублируется и не перепроверяется: если сценарию хочется заглянуть в статус или сравнить срок — правило живёт не там, где должно.

**Команды несут сырые строки** (`commands.go`). Разбор в `todo.NewTitle`, `todo.ParseTaskID` и прочие фабрики — работа сценария, поэтому будущий HTTP-слой останется тупым и о домене знать не будет. Разбирается всё до `load`: негодная команда не должна стоить чтения. Единственное исключение — срок, которому нужен тот же «сейчас», что увидит домен, поэтому он разбирается внутри мутатора и платит лишним чтением. Асимметрия сознательная и зафиксирована в тестах полем `wantReads` — «выравнивать» её не надо.

**Мутирующие сценарии собраны из одного хелпера** `mutate(ctx, taskID, ownerID, fn)` (`service.go`) — тот же приём, что `apply` в домене. Он делает четыре обязательных шага: `load` (подъём задачи со сверкой владельца), вызов домена, `repo.Save`, публикация. Новый сценарий писать по этому образцу; собственные поля разбирать до вызова `mutate`, а внутри — один вызов домена. Вручную повторять эти шаги нельзя: так теряются проверка владельца и публикация.

**Команда, ничего не изменившая, до записи не доходит.** После вызова домена `mutate` сверяет `task.Version()` с версией подъёма и на совпадении выходит с `nil`. Версию двигает только `apply`, общий хвост любой состоявшейся мутации, поэтому «версия та же» — это ровно «не произошло ничего». Дело не в лишней записи: она сверяется с версией, и чужая правка, случившаяся между `Get` и `Save`, вернула бы вызывающему `ErrVersionConflict` за изменение, которого он не делал. Доменное правило сценарий при этом не дублирует — что считать изменением, решает агрегат, здесь только читается его версия.

**Авторизация — здесь, а не в домене.** `Task` хранит `OwnerID` как идентичность и ни с чем его не сравнивает. Сопоставление владельца задачи с тем, кто её трогает, живёт в одном месте — `load(ctx, taskID, ownerID)` (`service.go`): разбор идентификаторов, `repo.Get`, сверка прав. Через него идут и `mutate`, и читающий `GetTask`, и обязан идти любой новый сценарий, работающий с существующей задачей. Пока подъём был расписан в обоих местах, следующий читающий сценарий списывался бы с `GetTask` — и однажды списался бы без проверки владельца.

**Чужая задача неотличима от несуществующей.** Отказ по владельцу возвращает `ErrTaskNotFound`, отдельной ошибки «нельзя» в контракте нет и заводить её не надо: она сообщала бы постороннему, что задача с таким идентификатором существует, и перебор превращался бы в разведку. Причина отказа остаётся в тексте ошибки — для человека, читающего лог, но не для `errors.Is`. Транспорту в итоге не нужно помнить про маскировку 403 в 404.

**Пустой приоритет трактуется по-разному** и это осознанно: в `CreateTaskCommand` пустая строка — обычный приоритет (нулевое значение `todo.Priority` осмысленно), в `ChangePriorityCommand` — ошибка, потому что команда «сменить приоритет неизвестно на какой» содержания не имеет.

**Порты** — `Repository`, `EventPublisher` и `Clock` (`ports.go`). Интерфейс объявляется у потребителя, а не у реализации: часы нужны только сценариям, поэтому и порт их.

**Версия подъёма живёт на границе, а не в домене.** `Get` возвращает `(task, loadedVersion, err)`, `Save` принимает `loadedVersion` обратно; сценарий это число не вычисляет, а переносит. «Откуда взялся этот объект в памяти» — вопрос хранилища: доменное поле, которое объясняется только через хранилище, доменным не является. Пробовали держать его в агрегате (`Task.loadedVersion`) — пришлось объяснять поле через базу и отдельно оговаривать, что сохранённый агрегат нельзя сохранить повторно, потому что он не узнаёт о собственной записи.

**Сверяться нужно именно с версией подъёма.** Выводить ожидаемую версию из сохраняемой (`stored+1 == incoming`) нельзя: писатель, накопивший две мутации, так молча затирает чужую запись, сделанную между его `Get` и `Save`. Это уже случалось — правило «на единицу больше» продержалось один заход ревью и было поймано только внешней проверкой. Число мутаций между `Get` и `Save` не ограничено: «создать, начать, записать один раз» законно и для вставки, и для обновления. Версию ведёт агрегат, хранилище её не назначает.

**`loadedVersion == 0` значит «не поднимал», а не «поднял нулевую версию».** Версия живой задачи всегда не меньше единицы, поэтому нуль однозначен, и в `switch` реализации ветка про занятое место обязана стоять раньше общей сверки версий. Стоя последней, она недостижима: сверка перехватывает случай первой и объясняет повторную вставку расхождением номеров вместо того, что произошло на самом деле. Ошибка при этом та же (`ErrVersionConflict`), расходятся только тексты — но текст ошибки читают в логе, когда всё уже сломалось.

**События публикуются синхронно после успешного `Save`.** Отказ доставки возвращается вызывающему как `*EventDeliveryError` и записи не отменяет — `CreateTask` в этом случае отдаёт идентификатор вместе с ошибкой. Различать отказ записи и отказ доставки обязан вызывающий: в первом случае не произошло ничего, во втором изменение состоялось и видно всем, кто прочтёт задачу. Оставлять это различие в тексте ошибки нельзя, поэтому `EventDeliveryError.Unwrap` отдаёт сразу две причины — `ErrEventDeliveryFailed` и отказ публикатора.

**Отмена запроса не отменяет доставку.** До записи отмена законна и останавливает работу: `Repository` обязан вернуть ошибку, из которой `errors.Is` достанет `context.Canceled`. После успешного `Save` всё наоборот — публикация идёт с `context.WithoutCancel(ctx)`, потому что задача уже изменилась и рассказать об этом надо независимо от того, ждёт ли ещё ответа тот, кто её заказал. Сценарий контекст сам не проверяет: отмена посреди работы всё равно ловится только тем, кто в этот момент работает.

**Недоставленные события уезжают в ошибке.** `PullEvents()` опустошает буфер агрегата, а агрегат живёт только внутри сценария, поэтому `EventDeliveryError` несёт сами события: иначе они исчезли бы вместе с ним и повторить доставку было бы нечем. Гарантии это не даёт — она появится с outbox'ом, когда события начнут писаться в одной транзакции с задачей. **Повторы и прочая политика доставки — дело реализации `EventPublisher`, а не сценария:** сценарий не знает, во что публикует и сколько это стоит. Nil вместо `NopPublisher` запрещён конструктором: это тихая потеря событий.

**Чтение отделено от изменения.** `GetTaskQuery` → `TaskView` (`queries.go`): плоское строковое представление из снимка, агрегат наружу не отдаётся. Чтение идёт мимо `mutate` — оно не порождает событий, не двигает версию и не нуждается в блокировке. Списки и фильтры, когда понадобятся, — отдельным портом запросов, а не расширением `Repository`.

**Необязательность выражается типом, а не флагом.** В `UpdateTaskCommand` все поля — указатели: `nil` значит «не менять», а не «поставить пустое». У срока три состояния, поэтому он `*DueDateUpdate`: `nil` — не трогать, пустая структура — снять, с `At` — назначить. Флаг `ClearDueDate` рядом с указателем дал бы то же самое, но позволил бы выразить противоречие «снять и назначить сразу»; здесь оно непредставимо.

**Outbox отложен до персистентного хранилища.** В хранилище на map его делать не на чем: транзакции, в одной с которой пишутся события, там нет. Пока живём с `EventDeliveryError`.

## Ошибки

**`%w` всегда последний, контекст — слева.** Обёртка описывает, что делали, причина остаётся в хвосте, и цепочка читается слева направо от внешнего действия к корню:

```
app: mutate task e0443c5f…: todo: task is already completed
app: build task service (task repository): app: missing dependency
todo: parse task id (length 3, want 32): todo: invalid task id
```

Сентинель — такая же причина, как чужая ошибка, поэтому `fmt.Errorf("%w: подробности", ErrX)` не писать: на `errors.Is` позиция `%w` не влияет вообще, так что выбор чисто про читаемость, а перевёрнутый порядок ломает цепочку. Подробности идут в скобках перед двоеточием: `fmt.Errorf("infra: save task %s (loaded version %d, stored version %d): %w", …, app.ErrVersionConflict)`. Текст перед двоеточием называет операцию и не пересказывает сентинель, иначе выходит «task not found: задача не найдена». Единственное исключение — `ParseTaskID`, где `%w: %w` несёт сразу классификацию и причину от `hex`.

**Тексты ошибок — по-английски, в нижнем регистре, без точки в конце и без «failed to».** Это относится и к сентинелям, и к обёрткам, и к тестовым двойникам: ошибки читают логи и поиск по трекеру, а не человек за спиной. Комментарии, названия подтестов и диагностика в `t.Errorf` остаются русскими — их аудитория другая.

**Префикс пакета** (`todo:`, `app:`, `infra:`) ставится в сентинелях и в обёртках, порождающих ошибку на месте. Пробрасывая чужую ошибку без своего контекста, префикс не добавлять — он уже есть внутри.

## Тесты

Живут в `package todo_test` и `package app_test` — оба слоя проверяются через публичный API, как их будет использовать вызывающая сторона.

**Таблицы операций общие.** `fieldMutations()` и `statusMutations()` в `task_test.go`, `taskMutations()` в `internal/app/service_test.go` перечисляют мутации один раз, и их переиспользуют все тесты, которые обходят операции. Добавляя мутатор в `Task` или сценарий в `TaskService`, добавить его в соответствующую таблицу — тогда он автоматически попадёт под проверки терминальных статусов, `updatedAt`, авторизации и конфликта версий.

Хелперы `mustTitle`, `mustTaskID`, `mustDueDate`, `newTestTask` — в `helpers_test.go`, все с `t.Helper()`. Опорный момент времени — `testNow`, производные — `testLater`, `testMuchLater`, `testEvenLater`, `testTomorrowAt`.

**Подставные зависимости app-слоя** — в `internal/app/fakes_test.go`. `fakeRepository` хранит именно снимки, а не указатели на агрегат: иначе сценарий, забывший `Save`, «сохранял» бы изменения через общий объект и тест этого не заметил бы. Правила блокировки в двойнике повторяют настоящие: упрощённый двойник перестаёт ловить то, на чём споткнётся оригинал, — на этом уже терялась дыра с потерянным обновлением.

**Совпадение реализаций порта проверяется набором, а не глазами.** У `app.Repository` их уже две — `InMemoryTaskRepository` и `fakeRepository`, — и разъезжались они молча: двойник панике́й отвечал там, где порт требует ошибку. Поэтому поведение порта описано один раз в `apptest.RepositoryContract(t, newRepository)` (`internal/app/apptest/repository.go`), и обе реализации прогоняются через него — `internal/app/contract_test.go` и `internal/infra/contract_test.go`. Своих тестов поведения у `InMemoryTaskRepository` нет: всё, что у него было, — это обещания порта, и держать их копию рядом значит завести третью версию правды.

**Разъезжаться реализациям положено, но не в поведении.** `sync.Mutex` против `sync.RWMutex`, имена полей, префиксы в текстах ошибок, инъекция отказов, хук `beforeSave`, счётчик записей — собственное дело каждой; сводить их к общему коду не надо, иначе средства теста уедут в `internal/infra`. В набор идёт только то, на что вправе рассчитывать вызывающий; тексты ошибок туда не входят — контракт сверяет сентинели через `errors.Is`.

**Новую реализацию `app.Repository` начинать с подключения набора** — это её готовая красная фаза. Новое обещание порта дописывать в набор, а не в тесты одной реализации: иначе вторая про него не узнает.

**Проверка не должна быть невыполнимой.** Сравнение указателей из двух вызовов `Snapshot()` всегда даёт `false` — снимок клонирует их каждый раз, — поэтому изоляция состояния проверяется поведением: меняем через одну копию, смотрим на другую. Тест, который не может упасть, хуже отсутствующего: он создаёт видимость покрытия. Хук `beforeSave` изображает чужую запись, вклинившуюся между `Get` и `Save`. Часы — `stubClock`, время подставное, как и в домене.

Сравнивать моменты времени только через `Equal`/`After`/`Before`. Оператор `==` у `time.Time` сличает внутреннее представление, включая зону и монотонный отсчёт, — на этом уже был баг.
